# 并行执行问题分析报告（修正版）

## 问题现象

在两个脚本中观察到以下现象：

### 1. exp1_bestparams_noEarly.py（运行成功）
- **执行方式**：顺序执行11个数据集，1个进程
- **并行策略**：单进程内部16核并行（`n_jobs=-1`）
- **并行范围**：只对参数搜索使用Parallel
- **运行时间**：约23小时
- **状态**：✅ 可以正常运行完成

### 2. exp1_real_datasets.py（卡住不动）
- **执行方式**：11个进程同时运行，每个进程处理1个数据集
- **并行策略**：外部11进程并行，内部控制Parallel
- **并行范围**：数据集级别 + 参数搜索级别
- **状态**：❌ 卡住不动，无法继续执行

---

## 🔥 核心发现：两个脚本对MetaGB的并行处理完全不同！

**特点：**

- ✅ 函数 `_evaluate_single_param` 内部统一处理XGBoost和MetaGB
- ✅ **MetaGB在单进程环境下可以正常并行**

## 🚨 卡住的根本原因

### 原因1（最可能）：过度并行导致的资源耗尽

**并行规模对比：**

| 脚本 | 外部进程数 | 内部Parallel | 总并发任务 | MetaGB并行 |
|------|-----------|-------------|----------|-----------|
| exp1_bestparams_noEarly.py | 1 | 16核 | 16 | ✅ 支持 |
| exp1_real_datasets.py | 11 | 11核（-1） | **121** ❌ | ❌ 顺序执行 |

#### 为什么121个并发任务会导致卡死？

1. **内存爆炸**
   - 11个进程 × 2个模型（XGBoost+MetaGB）= 22个模型实例
   - 每个进程内部还有11个参数并行
   - 总内存需求远超物理内存

2. **CPU竞争**
   - 11个进程同时争抢CPU资源
   - 每个进程内部又是11核并行
   - 系统调度开销巨大

3. **Windows joblib的局限性**
   - Windows的joblib多进程在子进程再使用Parallel时可能出现死锁
   - 文件锁竞争（多进程同时写入日志）

---

### 原因2：MetaGB的混合并行策略冲突

在多进程环境下：
- exp1_real_datasets.py的11个进程：**数据集级并行**
- 每个进程调用trainer.py：MetaGB被强制顺序执行
- 但如果设置了`--n_jobs=-1`，XGBoost会在每个进程内并行

**冲突场景：**
```
进程1: wine_quality
  ├─ XGBoost: Parallel(n_jobs=-1) → 启动16个子进程
  └─ MetaGB: 顺序执行

进程2: concrete_compressive_strength
  ├─ XGBoost: Parallel(n_jobs=-1) → 启动16个子进程
  └─ MetaGB: 顺序执行

...
进程11: houses
  ├─ XGBoost: Parallel(n_jobs=-1) → 启动16个子进程
  └─ MetaGB: 顺序执行
```

**总子进程数：11 × 16 = 176！**

这远超16核CPU的承载能力，导致：
- 严重的上下文切换
- 系统无响应（看起来像"卡住"）

---

### 原因3：exp1_bestparams_noEarly.py 为什么能正常？

关键区别：

**exp1_bestparams_noEarly.py（第223行）的Parallel调用：**
```python
all_cv_results = Parallel(n_jobs=-1)(
    delayed(_evaluate_single_param)(..., model_type, ...)
)
```

- ✅ **直接调用Parallel，不经过trainer.py**
- ✅ **对model_type不做区分，XGBoost和MetaGB都并行**
- ✅ MetaGB可以在单进程环境下正常并行

**exp1_real_datasets.py通过trainer.py：**
```python
# trainer.py第649行
if n_jobs != 1 and model_type == 'xgboost':
    cv_results = Parallel(n_jobs=n_jobs, ...)  # 只对XGBoost
else:
    # MetaGB走这里，顺序执行
```

- ⚠️ **MetaGB强制顺序执行**
- ⚠️ 在多进程环境下可能触发joblib的bug

## 解决方案

### 🔧 方案1：限制数据集并行进程数（推荐）

**针对exp1_real_datasets.py：**

不要同时启动11个进程，改为：
```bash
# 每批只运行2-3个数据集
python Exp_New/exp1_real_datasets.py --n_jobs 4 \
  --dataset wine_quality \
  --dataset concrete_compressive_strength \
  --dataset airfoil_self_noise
```

**或者使用批处理脚本：**
```bash
# batch1
python Exp_New/exp1_real_datasets.py --n_jobs 4 \
  --dataset wine_quality \
  --dataset concrete_compressive_strength \
  --dataset airfoil_self_noise

# 等待完成后运行 batch2
python Exp_New/exp1_real_datasets.py --n_jobs 4 \
  --dataset houses \
  --dataset miami_housing \
  --dataset physiochemical_protein
```

**参数设置原则：**
```
外部进程数 × 内部n_jobs ≤ CPU核心数
例如：3个进程 × 4内核 = 12 ≤ 16
```

---

### 🔧 方案2：修改trainer.py让MetaGB支持并行

**注意：** 需要先测试MetaGB在Windows上的多进程兼容性

修改 [`trainer.py`](Exp_New/utils/trainer.py:649)：

```python
# 第649行改为
if n_jobs != 1:
    # 尝试并行（both XGBoost and MetaGB）
    # 使用threading backend避免多进程问题
    if logger:
        logger.info(f"Running parallel grid search with threading backend...")

    cv_results = Parallel(n_jobs=max(1, n_jobs // 2), backend='threading', verbose=0)(
        delayed(_evaluate_single_param_combination)(...)
        for param_dict in all_param_dicts
    )
else:
    # Sequential execution
    cv_results = []
    for i, param_dict in enumerate(all_param_dicts):
        cv_result = _evaluate_single_param_combination(...)
```

**注意事项：**
- 使用 `backend='threading'` 避免多进程问题
- `n_jobs // 2` 限制内部并行度
- 需要充分测试MetaGB的线程安全性

---

### 🔧 方案3：使用exp1_bestparams_noEarly.py的方式

## 总结

### 问题核心
**exp1_real_datasets.py试图运行11个进程，每个进程内部还有11核并行，总共121个并发任务远超16核CPU的承载能力，导致系统资源耗尽而卡住。**

### 数据切分问题？
❌ **完全没有问题**，数据切分逻辑一致。

### 为什么exp1_bestparams_noEarly.py能正常？
✅ 单进程内并行，外部无并发，MetaGB直接支持Parallel。

### 推荐解决方案
1. **短期**：限制exp1_real_datasets.py的数据集并行数为2-3个
2. **中期**：修改trainer.py让MetaGB使用threading backend
3. **长期**：设计更好的任务调度系统，自动控制总并发数
