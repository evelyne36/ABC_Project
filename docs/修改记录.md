## 2026-06-08 current_metagb 加速与 random200 工程记录

### 一、保留的加速实现

当前保留 C++ CPU hist updater 的自动 histogram build 策略：

```text
METAGB_HIST_BUILD_MODE=auto|row_serial|cf_parallel|row_parallel
```

默认 `auto` 会在较宽、节点工作量较大的场景选择 `cf_parallel`，利用 conditional-feature 维度并行构建 histogram；小数据或低工作量节点仍可走轻量路径，避免并行开销反噬。

最终保留口径：

```text
cf_parallel + metagb_hist_subtract=false
```

原因：代表性宽表测试中 `cf_parallel` 明显优于 row-serial 路径；而 hist subtraction 复测没有加速收益，反而因为保存/复制完整 3D node histogram 引入额外开销。

### 二、已尝试但回滚的方案

以下方案未保留：

| 方案 | 结果 | 处理 |
|---|---|---|
| blocked/tiled histogram build + immediate split evaluation (`cf_immediate`) | 与 `cf_parallel` 基本持平或略慢 | 回滚 |
| `InitOriginalBins` 并行 feature loop + `upper_bound` digitization | 速度更快，但 RMSE 明显变化 | 立即回滚 |
| `InitOriginalBins` 仅并行 feature loop，保留原 while digitization | RMSE 正常，但速度慢于当前默认 | 回滚 |

结论：不允许性能退化和精度变化的前提下，当前最佳保留方案仍是 `cf_parallel` 自动路径，并关闭 hist subtraction。

### 三、hist subtraction 收益复查

复测结论：

- 在 QSAR-TID-11 代表性宽表配置上，`hist_subtract=true` 比 `false` 慢约 1.7x 到 1.9x。
- 在 wine_quality 和 airfoil 这类较小/中等数据上，`hist_subtract=true` 也没有观察到稳定收益。
- 当前实现需要缓存或复制完整 3D histogram，缓存成本超过 sibling subtraction 带来的节省。

因此脚本默认改为：

```text
metagb_hist_subtract = false
```

`--metagb-hist-subtract` 仅保留给消融实验显式开启。

### 七、后续实验理念固化

补充记录当前对话中确认的实验解释口径：

1. 公平比较原版 standalone `metagb/` 与嵌入版 `current_metagb` 时，使用 `n_jobs=1`。原版 MetaGB 不使用 XGBoost 的 `n_jobs`，因此 `current_metagb` 在 `n_jobs=4/16` 下的收益属于嵌入版 XGBoost/OpenMP 内部并行收益，应单独解释。
2. 只跑 `xgb_cpu vs current_metagb` 的 Random200/Random500 主实验时，16 核服务器推荐 `--task-workers 16 --n-jobs 1`。nested CV 有大量独立任务，任务级并行比单模型内部多线程更适合作为默认吞吐策略。
3. `--task-workers 4 --n-jobs 4` 可作为宽表专项计时或单任务延迟测试；`--task-workers 1 --n-jobs 16` 不建议作为完整主实验默认配置，除非任务数量太少无法填满机器。
4. 性能结论应分层表述：小表 current 可能慢于原版；普通中大表单核大致持平到小幅更快；宽表单核仍有明显收益，多核下 `cf_parallel` 收益更明显。
5. `current_metagb` 是 XGBoost 叶子模型表达能力扩展，不应被表述为普通 `xgb_cpu` 的纯速度替代。它需要构建 conditional-feature by predictive-feature 统计，计算量天然高于标准 XGBoost hist。
6. `random200` 定位为低成本试跑、筛查和流程确认；最终主结果可继续使用 `random500`。
7. 宽表 benchmark 需要单独报告，不能只混入整体平均。`QSAR-TID-11.csv` 这类高维数据最能体现 histogram build 优化和 `cf_parallel` 的收益。

## 一、背景

本次优化目标是提升 MetaGB（CPU histogram updater）的训练效率，同时保持与原始串行版精度完全等价。分两个阶段实施：Step 1 并行化，Step 2 直方图减法。

---

## 二、问题排查过程

### 2.1 初步测试发现精度劣化

在 Step 2（直方图减法）实施后，对比测试发现：

- 确定性路径（`colsample_bytree=1, subsample=1`）：Δ ≈ 0.4%（eps 级，初判可接受）
- 随机路径（`colsample_bytree=0.7, subsample=0.7`）：Δ ≈ 4%（真实劣化）

即使关闭 subtraction（`metagb_hist_subtract=False`），差异依然存在，说明问题**不在减法本身**。

### 2.2 根本原因定位

通过 `diff` 对比两个版本，发现 `beforereview` 版引入了 `pred_train_value_cache_` 和 `leaf_train_value_cache_`，声明为 `std::vector<float>`。

问题所在：

```cpp
// beforereview 版（有 bug）
std::vector<float> pred_train_value_cache_;   // float 截断

// InitTrainValueCache 中：
value = static_cast<float>(TrainValue(ridx, pred_feature));  // double → float，精度丢失

// 直方图构建时：
auto x = pred_train_value_cache_[...];  // float，而原始版是 double
cf_slice[HistOffset(pi, bin)].Add(grad, hess, x);  // x 被截断后参与累积
```

```cpp
// beforereview_0603lowrisk 版（正确）
auto x = TrainValue(ridx, split_pred_features[pi]);  // 直接用 double
```

`float` 截断导致 `grad_x = grad * x` 和 `hess_xx = hess * x * x` 的累积出现数值误差，进而改变分裂决策和叶权重。

## 七、Step 1 并行化说明

并行化实现位于 `FindBestSplit`，对 `cond_features` 维度用 OpenMP 并行：

- 每个线程维护独立的 `local_best_gain / local_meta / local_best`
- `node_hist`（3D 直方图）在并行区域只读，无数据竞争
- 最终 reduce 取各线程最优分裂

相关成员变量：
```cpp
std::vector<std::vector<MetaGBStats>>   thread_hist_chunk_;
std::vector<std::vector<MetaGBBinSplit>> thread_split_;
```

## 八、Step 2 直方图减法说明

缓存结构：
```cpp
std::unordered_map<bst_node_t, std::vector<MetaGBStats>> node_hist_cache_;
```

语义：`parent_hist = left_hist + right_hist`（cond rows 分区，element-wise 加法）。

触发条件：同一棵树内 `cond_features / pred_features` 固定，`hist3d_size` 不变，  
`parent_it->second.size() == hist3d_size && sib_it->second.size() == hist3d_size` 时触发。

释放策略：两个孩子都处理完后立即 `erase(parent_it)`，避免内存堆积。

## 九、排查过程中的犯错经验

### 9.1 误把确定性路径的 eps 差异判为"可接受"

**过程**：初测时 `col=1, sub=1` 下 Δ=0.4%，认为是浮点加法顺序导致的正常 eps 级差异，放过了。  
**错误**：随机路径 Δ=4% 才触发深查，但两者实为同一个 bug（float 截断），只是确定性路径下截断误差恰好方向相抵、量级更小，伪装成了 eps 噪声。  
**教训**：并行化/cache 引入后，只要 max_delta > 0（而不是 < 1e-10），就应追查根因，不能以"量级小"为由接受。标准是 `max_delta == 0`（数学等价），而不是 `max_delta < 某阈值`。

---

### 9.2 第一反应怀疑减法（subtraction），但真正问题在 cache 类型

**过程**：精度劣化出现在 Step 2（直方图减法）实施之后，自然怀疑减法引入了浮点误差（parent - sibling 的减法顺序问题）。花了时间分析 `parent_hist = left_hist + right_hist` 的数学等价性，以及 `hist3d_size` 一致性判断。  
**错误**：减法本身数学正确，问题早在 Step 1（cache 优化）引入时就存在，只是被 Step 2 的对比测试首次暴露。  
**教训**：精度问题的根因不一定在最近一次改动里。应先 **关闭最新改动**（`metagb_hist_subtract=False`）单独测试，如果差异仍然存在，说明问题在更早的代码里。这步隔离应该是排查第一步，而不是在怀疑减法一段时间后才做。

---

### 9.3 `BestLeaf` 用 float cache 也会影响树结构，不只影响叶权重

**过程**：最初判断 float 截断只影响叶节点的 `weight`（leaf value），不影响分裂判断，因为分裂逻辑走的是 `pred_train_value_cache_` 而 `BestLeaf` 只决定 `best_leaf_feature`。  
**错误**：`BestLeaf` 选出的 `best_leaf_feature` 写入了 `p_tree->SetMetaGBLeaf(nidx, best_leaf_feature)`，这改变了树节点的元数据；而 subtraction 路径中查询 `LeftChild() / RightChild()` 依赖树结构，导致子树的 hist 计算发生连锁变化。  
**教训**：leaf feature 的选择虽然不影响分裂特征（split_index），但作为树元数据会影响后续节点的处理。修改 pred 值的精度会通过 `SetMetaGBLeaf` 传播到整棵树。

---

### 9.4 忽略了 `float` 和 `double` 在 `TrainValue` 返回值上的差异

**过程**：`TrainValue()` 返回 `double`，`InitTrainValueCache` 中 `static_cast<float>(...)` 看起来只是一个常规的类型转换，没有立刻意识到这会在直方图累积时放大。  
**错误**：`grad_x += grad * x` 中 `x` 是 float 转 double 后的截断值，每一行样本都带入截断误差，100 行累积后误差被放大到足以改变 gain 排序和分裂决策。  
**教训**：cache 的目的是性能（避免重复计算），但引入 cache 时精度类型必须与原始计算路径一致。`float` 缓存用于 `double` 累积时，看似无害的类型转换会被循环放大。

---

### 9.5 对 `metagb_leaf_only_use_bias=True` 路径的误判

**过程**：为排除 `BestLeaf` 的 float cache 影响，测试了 `metagb_leaf_only_use_bias=True`（此时 BestLeaf 只用 bias=1.0，不走 float cache），结果差异依然存在，一度以为 `BestLeaf` 的 float 问题被排除了。  
**错误**：`BestLeaf` 路径只是不再读 `pred_train_value_cache_`，但**直方图构建路径**（`FindBestSplit` 的 hist 累积部分）仍然读同一个 float cache，分裂决策的 float 误差来源未被消除。两个来源叠加，关掉一个后差异仍存在。  
**教训**：用参数隔离某个代码路径时，要确认 float cache 在该参数下是否**完全不被读取**，而不是只关注最显眼的那个调用点。

---

### 9.6 迭代修补而非理解全貌

**过程**：前几轮排查都是在尝试"关掉某个参数看差异是否消失"，缺少系统性的全局 diff 分析。  
**教训**：两个版本出现不可解释的精度差异时，最有效的方法是直接 `diff` 两个文件全文，逐条看每一处改动的语义。本次最终靠 `diff` 一次定位了根因，前面的大量假设验证都是绕路。应该把 `diff` 全文作为**第一步**，而不是最后手段。
