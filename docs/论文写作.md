# current_metagb 论文写作与实验设计规划

## 一、核心论文定位

`current_metagb` 不应被定位为普通 `xgb_cpu` 的纯速度替代，而应定位为：

```text
在 XGBoost 框架内，将常数叶子扩展为特征选择的局部线性叶子；
通过 conditional feature 和 predictive feature 解耦，提高树模型对
局部线性响应、特征依赖异质性、高维/稀疏/时序特征的表达能力；
同时保持 XGBoost 训练、预测、sklearn API、分类/多分类目标函数的工程兼容性。
```

建议主贡献写成四点：

1. **Method**：提出/实现 `beta * x_ij` 的 feature-selected local linear leaf，严格包含 bias leaf，因此可退化为普通 XGBoost leaf。
2. **System**：把 MetaGB 嵌入 XGBoost CPU hist updater，支持 regression、binary、multiclass，保留 XGBoost pipeline。
3. **Optimization**：针对 3D histogram build 做 row-major cache、`cf_parallel`、auto mode 等优化，并明确 hist subtraction 当前不作为默认。
4. **Empirical Analysis**：通过 RandomSearch、pred fraction 消融、synthetic/time-series 分析说明 MetaGB 什么时候有效，什么时候不值得用。

一句话总故事线：

```text
We extend XGBoost leaves from constants to feature-selected local linear responses,
implement the resulting MetaGB objective inside the XGBoost hist framework, and show
through controlled nested-CV benchmarks, pred-fraction ablations, and synthetic/time-series
stress tests when this additional leaf expressiveness improves tabular prediction and
when ordinary XGBoost remains the better tradeoff.
```

## 二、论文结构建议

### 1. Introduction

- 树模型在 tabular data 中仍然强势。
- 标准 GBDT/XGBoost leaf 是常数，表达局部线性关系时需要更多树和更深结构。
- MetaGB 的核心直觉：一个区域内，响应可能更像 `beta * feature`，而不是常数。
- 本文问题：能否在 XGBoost 体系内高效、统一、可复现地实现这种 leaf extension，并在真实/合成/时序数据上验证其边界？

### 2. Related Work

- GBDT/XGBoost/LightGBM/CatBoost。
- model trees / linear leaves / piecewise linear trees。
- tabular benchmark 与 AutoML/TabArena。
- local feature selection / sparse local models。
- time-series/tabular feature engineering with tree models。

### 3. Methodology

- XGBoost constant leaf scoring。
- MetaGB leaf scoring：`grad_x`、`hess_xx`、`beta_j`。
- conditional feature vs predictive feature。
- bias feature 如何保证 strict extension。
- regression/binary/multiclass 的统一二阶优化。
- scalar multiclass 作为主路径；vector branch 作为 appendix/ablation。
- system optimization：3D hist、`cf_parallel`、hist subtraction 复查结论。

### 4. Experiments

- E0 baseline alignment。
- E1 main RandomSearch。
- E2 pred0 ablation。
- E3 preprocessing robustness。
- E4 pred fraction sensitivity。
- E5 detailed/fixed grid analysis。
- E6 synthetic。
- E7 time-series。

### 5. Analysis

- win/tie/loss。
- 按 dataset property 分组：样本量、特征数、稀疏度、类别特征比例、非线性程度。
- pred fraction 偏好。
- CV/Test gap。
- runtime tradeoff。

### 6. Conclusion

- 什么时候值得用 MetaGB。
- 什么时候 XGBoost 足够。
- 后续：GPU、better histogram reuse、time-series specialization。

## 三、实验主线设计

实验应收敛成三层：

```text
Layer A: 确认性主实验
Layer B: 机制性消融
Layer C: 边界与特性实验
```

不要把实验摊成所有维度全排列。更好的策略是：

```text
主实验少而硬
消融准而深
附录广而稳
```

## 四、Layer A：确认性主实验

这是论文主表，必须干净、可复现、审稿人一眼能懂。

主实验：

```text
XGBoost RandomSearch600
vs
current_metagb RandomSearch600
```

候选设置：

```text
MetaGB:
  pred_feature_fraction = 0.1, 0.2, ..., 1.0
  score_agg = 0, 1, 2
  每个 pred × score_agg 联合组合 20 组
  总计 600 candidates

XGBoost:
  600 shared-backbone candidates
  总计 600 candidates
```

任务：

```text
regression
binary classification
multiclass classification
```

CV：

```text
outer 5 folds
inner 4 folds
nested CV
outer test 只用于最终报告
inner CV 用于选超参
```

指标：

```text
regression: RMSE, lower better
binary: AUC + logloss
multiclass: logloss + accuracy/balanced accuracy
runtime: inner train time, final train time, total train time
```

统计：

```text
per dataset: best outer test score mean/std
overall: win/tie/loss
relative improvement %
rank average
paired bootstrap / Wilcoxon / critical-difference style ranking
```

主文 preprocessing 建议：

```text
Drop
OneHot
```

`Ordinal` 放 appendix 或 robustness。原因是 ordinal 对树模型可能引入人为顺序和 split bias，不适合作为唯一主结果口径。

## 五、Layer B：机制性消融

这一层回答：

```text
MetaGB 为什么有效？
pred_feature_fraction 是否真的重要？
```

### 1. pred0 ablation

对比：

```text
current_metagb_pred0 vs xgb_cpu
```

目的：

- 检查 bias/退化路径。
- 证明 MetaGB 的收益来自 predictive feature leaf，而不是 pipeline 差异。
- 如果 pred0 与 XGB 不完全一致，需要解释参数、leaf scoring、implementation path 是否仍有差别。

### 2. pred fraction sensitivity

对 `pred_feature_fraction=0.1..1.0` 分组统计：

```text
每个 pred bucket 的 inner CV mean/std
outer test score
selected frequency
不同数据集上的最优 pred 分布
```

核心解释：

```text
pred fraction 不是普通调参维度，而是控制“局部线性叶子表达容量”的结构参数。
```

建议图：

- x 轴 pred fraction，y 轴 RMSE/logloss。
- 每个数据集一条淡线，平均一条粗线。
- 按高维/低维、稀疏/稠密分组。

### 3. fixed backbone pred sweep

从 XGB best 或 MetaGB best backbone 出发，只扫 pred：

```text
XGB-best backbone + pred 0.0..1.0
MetaGB-best backbone + pred 0.0..1.0
```

目的：

- 分离“普通超参搜索收益”和“pred feature 机制收益”。
- 判断 CV 选不出好 pred 是过拟合还是搜索空间耦合问题。

## 六、Layer C：边界与特性实验

这一层是顶会论文里最能体现 insight 的部分。

### 1. Synthetic

至少设计 4 类：

```text
A. constant leaf friendly:
   y = piecewise constant + noise
   预期 XGBoost 强，MetaGB 不一定强

B. local linear response:
   if x0 > threshold: y = beta1 * x3
   else: y = beta2 * x7
   预期 MetaGB 强

C. conditional-predictive decoupling:
   split feature 和 predictive feature 明确不同
   例如 region by x0/x1, response by x5/x8

D. high-dimensional sparse/noisy:
   有少数 predictive features，大量 irrelevant features
   测 pred fraction 稳定性和 feature selection 能力
```

报告：

```text
性能
选中的 predictive feature 是否命中真实 feature
pred fraction 偏好
噪声增强下的稳定性
```

### 2. Time-series

时序不要用 random CV。建议：

```text
rolling-origin split
lag features
calendar/statistical rolling features
target = next-step or horizon-h step
```

对比：

```text
xgb_cpu
current_metagb
simple baselines 可放 appendix: persistence / linear / random forest
```

重点不是“时序模型大战 Transformer”，而是证明：

```text
当滞后特征在不同阶段有不同局部线性影响时，MetaGB leaf 有合理优势。
```

必须强调 leakage control：

```text
所有 rolling/stat features 只能用过去
split 按时间顺序
normalization 如使用，只能 fit on train
```

## 七、Normalization 策略

建议主实验不做 normalization，或者只放 appendix。

原因：

- 树模型通常不需要 feature normalization。
- 对 y normalization/denormalization 容易引起审稿人质疑 leakage。
- MetaGB 的 `beta * x_ij` 对特征尺度更敏感，因此 normalization 是一个值得分析的变量，但不适合作为主线维度无限展开。

建议写法：

```text
Main experiments use raw numeric values after categorical processing.
Normalization is evaluated as an appendix robustness check with train-only fit statistics.
```

## 八、Categorical Handling 策略

主文：

```text
Drop
OneHot
```

Appendix：

```text
Ordinal
```

解释：

- Drop：检查纯数值特征场景，避免类别编码干扰。
- OneHot：保留类别信息，更接近真实 tabular pipeline。
- Ordinal：树模型能处理，但人为顺序可能引入不真实 split bias，因此作为 robustness。

## 九、RandomSearch 范围与公平性

论文中建议写：

```text
XGBoost and MetaGB use paired candidates from the same shared backbone search space.
MetaGB jointly and evenly searches 10 pred_feature_fraction values and score_agg in {0, 1, 2}.
```

公平性重点：

- XGB 和 MetaGB candidate 数量相同。
- MetaGB pred buckets 均衡。
- XGB 与 MetaGB 的第 `i` 个候选使用相同公共 backbone。
- Random300 是固定 seed 下 Random600 的前 300 个候选。
- MetaGB 均衡覆盖 30 个 `pred_feature_fraction × score_agg` 联合组合；
  Random300/Random600 中每个组合分别有 10/20 个候选。
- 对同一 task family，提前生成并冻结统一 candidate bank；Drop、OneHot 和 Ordinal
  复用相同的候选参数池和相同 CV seed，避免 preprocessing 之间因随机抽样到不同参数
  组合而产生额外比较噪声。
- 每个 `dataset × preprocessing × model × outer fold` 仍在自己的 inner CV 中，从
  固定 candidate bank 独立选择最佳参数。固定的是候选池，不是最终选中的参数。
- Regression 使用固定 Random600 candidate bank；Binary 和 Multiclass 暂使用固定
  Random300 candidate bank。若 binary 与 multiclass 使用相同 seed、相同 search-space
  文件和相同 models，则二者生成的候选参数池也保持一致。

当前实现中的候选池确定性条件：

```text
相同 --seed
相同 --max-candidates
相同 --search-space-json
相同 models
```

满足上述条件时，Random300/Random600 在不同运行及 Drop/OneHot/Ordinal 实验中会生成
相同 candidate bank。每次运行生成的实际候选池保存于：

```text
results/<run_id>/candidate_configs.json
```

正式实验应保存并校验该文件，作为候选池一致性的复现证据。

论文中建议使用以下表述：

```text
For each task family, we generate and freeze a common random-search candidate bank
before running the experiments. The same candidate bank and cross-validation seeds
are reused across preprocessing conditions. Hyperparameters are independently
selected for each dataset and preprocessing condition using inner cross-validation,
while the outer test folds remain untouched.
```

不建议先在某一种 preprocessing 或数据集上选出一套“全局最佳参数”，再固定应用于
Drop、OneHot 和 Ordinal。不同 preprocessing 会改变特征数量、稀疏度与有效分裂空间，
其合理最佳参数可能不同。固定候选池属于公平控制；固定最终最佳参数会不公平地限制某些
preprocessing。

仍需注意的 preprocessing 公平性限制：

- 当前工程在 outer split 前完成 Drop/OneHot/Ordinal 处理；严格论文实验应尽量采用
  fold-local preprocessing，即只在训练折拟合编码规则，再应用于验证/测试折。
- 不同 preprocessing 可能因缺失值处理保留不同样本行。正式比较应固定原始 row-level
  fold IDs，并确保不同 preprocessing 的 outer-test 样本集合一致。

当前实验规划为 regression 使用 Random600，binary 与 multiclass 使用 Random300；
三种 preprocessing 均复用对应 task family 的固定候选池。

## 十、计算资源策略

正式主实验：

```text
--task-workers 16 --n-jobs 1
```

不要主实验默认用 `4x4`。原因：

- `n_jobs=4` 会给 current_metagb 额外并行收益。
- 原版 MetaGB 不吃 `n_jobs`。
- 完整 nested CV 有大量独立 task，任务级并行吞吐更稳。

如果单独报告 system speedup：

```text
single-thread fairness: n_jobs=1
multi-thread engineering speedup: n_jobs=4/16
```

二者分开写。

## 十一、建议的最终实验矩阵

主文控制在这个规模：

```text
Main:
  datasets: TabArena regression/binary/multiclass
  preprocessing: Drop + OneHot
  models: xgb_cpu vs current_metagb
  search: Random600
  CV: outer5 inner4
  seeds: 1 primary seed，必要时 top-level repeat 3 seeds 做 robustness

Ablation:
  pred0 vs xgb
  pred fraction 0.1..1.0 group analysis
  fixed backbone pred sweep

Analysis:
  runtime
  win/tie/loss
  CV/Test gap
  dataset property grouping

Additional:
  synthetic
  time-series
  ordinal appendix
  normalization appendix
```

不建议一开始就做：

```text
3 seeds x 3 preprocessing x 2 normalization x all datasets x Random600
```

这会爆炸，而且论文叙事不一定更强。

## 十二、关键图表设计

至少准备这些：

1. **Main performance table**
   - 每个 task type 一个表。
   - XGB vs MetaGB。
   - mean outer test metric。
   - best 用 bold。
   - 旁边放 relative improvement。

2. **Win/Tie/Loss summary**
   - 按 regression/binary/multiclass。
   - Drop/OneHot 分开。

3. **Pred fraction heatmap**
   - rows = datasets。
   - columns = pred fraction。
   - value = relative CV/test performance。
   - 这是最能体现 MetaGB 独特性的图之一。

4. **Runtime scatter**
   - x = XGB train time。
   - y = MetaGB train time。
   - 点大小 = feature count。
   - 标出宽表。

5. **CV/Test gap plot**
   - x = inner CV rank。
   - y = outer test performance。
   - 分析 CV 是否稳定选出好 pred。

6. **Synthetic mechanism figure**
   - 展示 true conditional feature 和 true predictive feature。
   - 报 selected predictive feature hit rate。

7. **Critical difference / average rank**
   - 若数据集足够多，能提升统计说服力。

## 十三、审稿风险与应对

### 1. “你只是调参更多？”

应对：

- XGB 和 MetaGB candidate 数量相同。
- MetaGB pred buckets 均衡。
- 做 pred0 ablation。
- 做 fixed backbone pred sweep。

### 2. “为什么不用 XGBoost 自带 categorical 或只用一种编码？”

应对：

- Drop/OneHot 主实验。
- Ordinal appendix。
- 所有模型同一 preprocessing。

### 3. “MetaGB 比 XGB 慢很多是否值得？”

应对：

- 不卖速度替代，卖表达能力扩展。
- 报告 runtime-quality tradeoff。
- 指出宽表和特定 synthetic/time-series 场景收益。

### 4. “CV 选择不稳定？”

应对：

- 把它变成分析贡献。
- 展示 pred sensitivity。
- 展示 CV/Test gap。
- 展示 Top-k stability。

### 5. “synthetic 太人造？”

应对：

- synthetic 只用于机制验证。
- 真实 TabArena 是主证据。
- time-series 是外部泛化。

## 十四、执行优先级

建议按这个顺序开展：

1. **E0 Baseline alignment**
   - 先确保 XGB 与 TabArena/既有结果大体对齐。
   - 若无法对齐，先排数据处理、fold、metric、参数口径。

2. **Random600 main**
   - 跑 `xgb_cpu vs current_metagb`。
   - 优先 Drop + OneHot。
   - `--task-workers 16 --n-jobs 1`。

3. **pred0 ablation**
   - 解释退化路径和 pipeline 差异。

4. **pred fraction analysis**
   - 从主实验结果直接抽取 heatmap、selected frequency、bucket performance。

5. **fixed backbone pred sweep**
   - 针对代表性 positive/negative cases 做深挖。

6. **synthetic**
   - 机制验证，争取做出清晰可解释的 positive case。

7. **time-series**
   - 作为外部场景扩展，严格避免 leakage。

8. **appendix robustness**
   - Ordinal。
   - normalization。
   - 3 seeds。

## 十五、材料提交范式

每次实验汇报建议按以下格式：

```text
Abstract Conclusion
  一句话说明最重要结论。

Summary Description
  实验设置、数据、模型、参数、CV、指标。

Detailed Analysis
  分任务、分数据集、分 pred、分 preprocessing 的分析。

Raw Data
  summary.csv / aggregate.csv / candidates.csv / pred_fraction_analysis.csv。
```

写 paper 时优先展示：

```text
什么现象稳定存在？
MetaGB 在哪里赢？
在哪里输？
为什么？
代价是什么？
这个代价是否值得？
```
