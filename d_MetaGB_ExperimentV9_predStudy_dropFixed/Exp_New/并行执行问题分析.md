# 并行执行问题分析报告

## 问题现象

在两个脚本中观察到以下现象：

### 1. exp1_bestparams_noEarly.py（运行成功）
- 只使用 `n_jobs=-1`（使用所有CPU核心）
- 运行时间约23小时
- **可以正常运行完成**

### 2. exp1_real_datasets.py（卡住不动）
- 尝试同时拉取11个数据集作为进程并行
- **卡住不动，无法继续执行**

---

## 根本原因分析

### 核心问题：数据切分方式不同

#### exp1_bestparams_noEarly.py 的数据切分
```python
# 第326-328行
X_train_outer, X_test_outer, y_train_outer, y_test_outer = train_test_split(
    X, y, test_size=0.2, random_state=RANDOM_SEED
)
```
**特点：**
- 使用简单的 **random_state** 进行一次性切分
- 所有参数组合共享相同的训练/测试切分
- 数据在内存中只有一份

#### exp1_real_datasets.py 的数据切分
```python
# 第320-323行
X_train, X_val, y_train, y_val = sklearn_split(
    X_train_full, y_train_full, test_size=0.2, random_state=seed
)
```
**特点：**
- 同样使用 random_state 切分
- 但是嵌套在 GridSearchCV 的 KFold 中

---

### 关键差异点

#### 1. **MetaGB 并行冲突**（主要原因！）

在 [`trainer.py`](Exp_New/utils/trainer.py:649) 的 GridSearchCV 函数中：

```python
# 第649-670行
if n_jobs != 1 and model_type == 'xgboost':
    # Parallel execution for XGBoost (MetaGB may have issues with parallel)
    cv_results = Parallel(n_jobs=n_jobs, verbose=0)(
        delayed(_evaluate_single_param_combination)(...)
        for param_dict in all_param_dicts
    )
else:
    # Sequential execution
    cv_results = []
    for i, param_dict in enumerate(all_param_dicts):
        ...
```

**关键发现：**
- **MetaGB 被强制使用顺序执行**（else分支）
- 代码注释明确说明：`MetaGB may have issues with parallel`
- 这是因为 MetaGB 的 CFFI 库在 Windows 多进程环境下有兼容性问题

#### 2. **exp1_real_datasets.py 没有实现数据级并行**

在 [`exp1_real_datasets.py`](Exp_New/exp1_real_datasets.py:616) 的主循环中：

```python
# 第616-638行
for dataset_name, csv_path in datasets:
    try:
        results = run_experiment_for_dataset(
            dataset_name=dataset_name,
            csv_path=csv_path,
            seed=seed,
            logger=logger,
            results_dir=results_dir,
            logs_dir=logs_dir,
            plots_dir=plots_dir
        )
        all_results.extend(results)
```

**问题：**
- 这是一个**顺序执行**的 for 循环
- 一次只处理一个数据集
- 即使设置了 `--n_jobs=11`，也只是改变了**参数搜索的并行度**，并没有实现数据集级别的并行

---

## 为什么会卡住不动？

### 可能的场景：

#### 场景A：内存不足导致系统卡死
- 用户可能以为设置了 `--n_jobs=11` 会同时运行11个数据集
- 但实际上并没有数据级并行
- 如果用户尝试手动并行运行多个进程（例如同时启动脚本多次）
- Windows 的 joblib backend 在数据级并行时可能因以下原因卡住：
  - 文件锁冲突（多个进程同时写入日志文件）
  - 共享库（libmetagb）加载冲突
  - MetaGB 的 CFFI 库不支持 Windows 多进程

#### 场景B：参数搜索的内部并行与外部并行冲突
- 即使启动了 11 个数据集进程
- 每个进程内部还有 `n_jobs=11` 的参数搜索并行
- 总并行度 = 11 数据集 × 11 jobs = 121 个并发任务
- 这会严重超出 CPU 核心数，导致：
  - 上下文切换开销巨大
  - 系统响应缓慢
  - 可能出现死锁或资源竞争

---

## 数据切分是否有问题？

### 答案：**数据切分没有问题**

两个脚本都使用了相同的 `random_state` 进行数据划分，切分逻辑是一致的。

实际问题是：
1. **没有实现数据集级别的并行**
2. **MetaGB 不支持 Windows 多进程并行**
3. **过度的并行配置可能导致系统卡死**

---

## 解决方案建议

### 方案1：修复 exp1_real_datasets.py 实现真正的数据级并行

在 exp1_real_datasets.py 的主循环中使用 Parallel：

```python
from joblib import Parallel, delayed

def run_single_dataset(dataset_name, csv_path, seed, results_dir, logs_dir, plots_dir):
    return run_experiment_for_dataset(
        dataset_name=dataset_name,
        csv_path=csv_path,
        seed=seed,
        logger=None,  # 多进程时不能共享logger
        results_dir=results_dir,
        logs_dir=logs_dir,
        plots_dir=plots_dir
    )

# 使用并行处理数据集
all_results_list = Parallel(n_jobs=args.n_jobs)(
    delayed(run_single_dataset)(name, path, args.seed, results_dir, logs_dir, plots_dir)
    for name, path in datasets
)

# 合并结果
for results in all_results_list:
    all_results.extend(results)
```

**注意事项：**
- 每个数据集进程需要独立的 logger
- 日志文件需要按进程ID区分（避免冲突）
- 不适合在 Windows 上使用（MetaGB 兼容性问题）

### 方案2：保持顺序执行，但优化单个数据集的并行度

**推荐方案：**
- **数据集级别：顺序执行**（一次运行一个数据集）
- **参数搜索级别：使用适当的并行度**（n_jobs = CPU核心数 / 2）

修改 exp1_real_datasets.py 的默认参数：
```python
parser.add_argument('--n_jobs', type=int, default=4,  # 修改为4而不是1
                    help='Number of parallel jobs for grid search. -1 uses all CPUs (default: 4)')
```

### 方案3：只在 exp1_bestparams_noEarly.py 中并行（当前方案）

**优点：**
- 经过验证的可行方案
- 避免了 MetaGB 并行兼容性问题
- 稳定性高

### 方案4：使用多线程代替多进程

在 Windows 上，多线程对 CFFI 库的兼容性更好：

```python
from joblib import Parallel, delayed

cv_results = Parallel(n_jobs=n_jobs, backend='threading', verbose=0)(
    delayed(_evaluate_single_param_combination)(...)
    for param_dict in all_param_dicts
)
```

**风险：**
- Python GIL 限制，性能提升有限
- 需要测试 MetaGB 是否线程安全

## 最佳实践建议

### 1. 数据集级并行（Linux推荐）
```bash
# 使用 GNU parallel 或 xargs
ls dataset/*.csv | parallel -j 4 python exp1_real_datasets.py --dataset {.}
```

### 2. 参数搜索级并行（Windows推荐）
```bash
# 逐个运行数据集，但在参数搜索中使用并行
python exp1_real_datasets.py --n_jobs 4 --dataset wine_quality
python exp1_real_datasets.py --n_jobs 4 --dataset concrete_compressive_strength
```

### 3. 避免 n_jobs=-1 在多进程环境
- `n_jobs=-1` 意味着使用所有 CPU 核心
- 如果在数据级并行的环境下使用，会导致过度的并行
- **建议使用具体的数值**（如：n_jobs=4）

| 问题 | 答案 |
|------|------|
| **数据切分有问题吗？** | 没有，两个脚本的数据切分逻辑一致 |
